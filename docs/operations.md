# Operations

How to run pulsar and carry out the tasks it needs. The settings are in
[configuration.md](configuration.md).

## Starting it

pulsar keeps its state in PostgreSQL, in a database that must exist. It
serves at once, and meanwhile applies its migrations and loads its signing
keys, generating the first one if the database holds none.

- Until both are done, `/readyz`, the JWK Set and every protocol endpoint
  and page but discovery and cross-origin preflights answer 503. pulsar
  exits if either fails.
- After that, `/readyz` answers 200 while a ping through its connection
  pool succeeds, and 503 when one fails. `/livez` answers 200 while the
  process serves.
- The Login Session cookie is `Secure`, which browsers keep over plain
  http only on `localhost`.

The README's [Quickstart](../README.md#quickstart) starts it on a local
database.

## Rotating the signing key

`pulsar keys rotate` stores a new signing key and exits. It reads the same
environment as the server.

```sh
# The same environment as the server's, PULSAR_SECRET included.
PULSAR_ISSUER=http://localhost:8080 \
  PULSAR_DATABASE_URL='postgres://localhost:5432/pulsar?sslmode=disable' \
  PULSAR_REGISTRY=conformance/registry.json \
  go run ./cmd/pulsar keys rotate
```

The new key is published before it signs, and the old one stays published
until every token it signed has expired:

| When, after the key is stored | What happens                                                                                                                 |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Within 1 minute               | Every replica publishes the new key in its JWK Set, at its next reload                                                       |
| 2 minutes                     | Every replica signs with the new key: one reload interval plus the JWK Set's one-minute cache                                |
| 13 minutes                    | The old key leaves the JWK Set, at each replica's next reload: the ten-minute token lifetime plus a reload interval, after 2 |
| 10 hours and 3 minutes        | pulsar stops accepting `id_token_hint`s the old key signed at logout ([behavior.md](behavior.md#logout))                     |

So, provided every replica reloads on time and Clients honor
`Cache-Control`, every replica, and every JWK Set a Client has cached, has
the new key before it signs anything.

- Run it only once every replica runs a version of pulsar with this
  schedule, since an earlier one signs with a new key at once.
- Run it on a host whose clock agrees with the replicas'.
- It refuses a database pulsar has never started against, and a
  `PULSAR_SECRET` other than the one the keys are stored under.
- It does not revoke a key. A leaked key stays in the JWK Set, so Clients
  accept tokens signed with it for at least 13 minutes after a rotation,
  and pulsar accepts `id_token_hint`s signed with it for 10 hours and 3
  minutes.

## Making a Client secret

`pulsar client-secret` generates a Client secret and prints it with its
hash, so that the secret is generated by the authorization server, as
RFC 6819 §5.1.4.2.2 has it. The secret is 256 bits from `crypto/rand` in
unpadded base64url, which needs no escaping in `client_secret_basic`, and
guessing cannot find it (RFC 6749 §10.10).

```sh
go run ./cmd/pulsar client-secret
# {"client_secret":"…","client_secret_hash":"$argon2id$v=19$m=19456,t=2,p=1$…$…"}
```

The command reads no configuration, and the secret is shown only in its
output: give `client_secret` to the Client and copy `client_secret_hash`
into the registry.

pulsar cannot tell how a hash was made, so it also accepts one made
elsewhere. The operator must then make the secret it hashes at least 256
bits from a cryptographically strong random source
([ADR 0005](adr/0005-logins-throttled-per-end-user-by-delay.md)).

## Hashing a password

pulsar has no command for End-User passwords. The `argon2` command of
Argon2's reference implementation
([phc-winner-argon2](https://github.com/P-H-C/phc-winner-argon2)) prints a
password's hash:

```sh
# 2 passes over 32 MiB, one lane: above OWASP's minimum for Argon2id.
read -rs password && printf %s "$password" | argon2 "$(openssl rand -hex 16)" -id -t 2 -m 15 -p 1 -e
```
