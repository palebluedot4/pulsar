# Generating and storing Client secrets

How other providers generate and store OAuth 2.0 Client secrets, what
the specifications and security guidance say about hashing a secret that
a machine generated, which characters survive `client_secret_basic`, and
whether secrets carry a prefix that secret scanners can find. Written
for #61, which proposes a `pulsar client-secret` command. Surveyed 2026-11-09
from specifications, official documentation and official source code at
these release tags: Keycloak `26.8.2` (`e514445f`), Ory Hydra `v26.2.0`
(`0b84568f`), Authelia `v4.39.28` (`8da42b23`), Zitadel `v4.20.2`
(`dce17d59`), Dex `v2.46.1` (`75eb1923`) and node-oidc-provider `v9.13.3`
(`7b21c6da`). Hosted providers were read from their API references.
Anything not confirmed is marked **UNVERIFIED**.

Already established in [login throttling](login-throttling.md), and not
repeated here: RFC 6749 §10.10 (guessing probability at most 2^(-128),
SHOULD be at most 2^(-160)), RFC 6819 §5.1.4.2.2 (">=128 bits … generated
by the authorization server"), OWASP's Argon2id minimum, and Hydra's
default PBKDF2.

## Argon2id parameters

OWASP's Password Storage Cheat Sheet (commit `87a1faf1`, 2026-10-30)
lists five minimum configurations, which "provide an equal level of
defense, and the only difference is a trade off between CPU and RAM
usage":

| m (KiB)        | t   | p   | Note                      |
| -------------- | --- | --- | ------------------------- |
| 47104 (46 MiB) | 1   | 1   | "Do not use with Argon2i" |
| 19456 (19 MiB) | 2   | 1   | "Do not use with Argon2i" |
| 12288 (12 MiB) | 3   | 1   |                           |
| 9216 (9 MiB)   | 4   | 1   |                           |
| 7168 (7 MiB)   | 5   | 1   |                           |

ASVS 5.0 Appendix C lists three: t = 1 with m ≥ 47104, t = 2 with
m ≥ 19456, t ≥ 3 with m ≥ 12288, each with p = 1.

The PHC string format is now specified by C2SP (commit `fc7f312a`; the
P-H-C repository says "MOVED"): `$argon2id$v=19$m=…,t=…,p=…$salt$hash`,
parameters "in the `m,t,p,keyid,data` order", salt and hash in "standard
Base64 encoding (RFC 4648, section 4) except that the padding `=` signs
are omitted". "The default byte length of the salt is 16 bytes (22
characters in B64 encoding)"; "The default output length is 32 bytes (43
characters)". `golang.org/x/crypto/argon2.IDKey` (v0.58.0) documents
RFC 9106's two recommended options and no others.

<https://github.com/C2SP/C2SP/blob/fc7f312a/phc-strings.md>,

### Authelia's CLI

The nearest existing tool to the command #61 proposes.

- `authelia crypto hash generate [argon2|bcrypt|pbkdf2|scrypt|sha2crypt]`
  with `--random` "uses a randomly generated password";
  `--random.length` "(default 72)"; `--random.charset` "options are
  'ascii', 'alphanumeric', 'alphabetic', 'numeric', 'numeric-hex', and
  'rfc3986' (default "alphanumeric")"; `--random.characters` sets an
  explicit alphabet; `--password` supplies one; `--no-confirm` skips the
  confirmation prompt.
- Without a subcommand it uses the configured file backend's password
  algorithm, which defaults to Argon2id, t=3, m=65536 KiB, p=4, 32-byte
  key, 16-byte salt. `argon2` takes `-i`, `-m`, `-p`, `-k`, `-s`,
  `--variant` with those defaults, and `--profile` "low-memory" or
  "recommended". `pbkdf2` defaults to SHA-512, with iterations
  "determined by the variant".
- Output, from `internal/commands/crypto_hash.go`:

  ```text
  Random Password: <secret>
  Random Password (URL Encoded): <secret>   # only if url.QueryEscape changes it
  Digest: $argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
  ```

- `authelia crypto rand` prints `Random Value: …` (and the URL-encoded
  line under the same condition), with `-n/--length` "(default 72)",
  `-x/--charset`, `--characters`, and `--file` to write values to files
  with mode `0600` instead of printing them.
- "since v4.38.0 Authelia has included a URL encoded value when
  generating random strings or password hashes if the URL encoded value
  differs from the non-encoded value."

## Slow or fast hash for a generated secret

- NIST SP 800-63B-4 §3.1.2.2 and ASVS 5.0 6.5.2 draw the same line: at
  112 bits or more, a hash with an approved function suffices; below it,
  a salted password hashing scheme is required. RFC 6819 §5.1.4.1.3
  adds a salt only for a credential that "lacks a reasonable entropy
  level". None of them requires a slow function for a 256-bit secret, and
  none forbids one.
- OWASP's Password Storage Cheat Sheet and ASVS 11.4.2 address passwords
  only.
- What providers do with generated secrets: Zitadel hashes them with
  bcrypt at cost 4, `golang.org/x/crypto/bcrypt`'s `MinCost`. Hydra uses PBKDF2-SHA256
  at 25,000 iterations, where OWASP's minimum for passwords is 600,000.
  GitLab stores OAuth access tokens "in PBKDF2+SHA512 format and
  stretched 20,000 times". Authelia recommends PBKDF2-SHA512 at 310,000
  and warns that "If your client operations time out, you might need to
  reduce the work factor".
- GitLab's personal access tokens are stored as a SHA-256 digest with an
  instance-wide salt, per its 2018 commit "Persist only SHA digest of
  PersonalAccessToken#token"; whether that holds in current releases is
  **UNVERIFIED**. GitHub's token-format post does not say how GitHub
  stores tokens.

Sources: <https://docs.gitlab.com/security/password_storage/>,
<https://gitlab.com/gitlab-org/gitlab-foss/-/commit/daed01a5ca348e7d267b50e325bf58185617a0ad>.

## Characters and `client_secret_basic`

- RFC 6749 allows any printable ASCII in a secret and requires it to be
  form-encoded before Basic. A server that follows §2.3.1 decodes it:
  Hydra (fosite), Dex and pulsar call `url.QueryUnescape` on both
  halves, and Authelia "enforces this practice". `golang.org/x/oauth2`
  encodes with `url.QueryEscape` before `SetBasicAuth`.
- With a client that skips the encoding, which the OAuth 2.1 draft says
  has happened, a `+` in the secret reaches the server as a space, and
  `url.QueryUnescape` fails on a `%` not followed by two hex digits.
  `/` and `=` decode to themselves and survive. Microsoft's documented
  example secret contains `[`, `@`, `+`, `]` and `:`; Cognito's pattern
  for custom secrets allows `+`.
- With an alphabet that form-encoding leaves unchanged, the step does
  not matter. Base64url without padding (`A-Za-z0-9-_`) and base32
  qualify under both WHATWG's serializer and Go's `url.QueryEscape`.
  RFC 3986's unreserved set, which Authelia and Hydra use, adds `.` and
  `~`; WHATWG's serializer encodes `~` but `%7E` decodes back to `~`.
- Authelia's FAQ: "When using `client_secret_basic` several
  implementations of OAuth 2.0 and OpenID Connect 1.0 do not properly URL
  encode these values as is absolutely required by the specification",
  and "we suggest ensuring the client id and client secret only use the
  unreserved characters". Its generators print a URL-encoded copy when it
  differs.
- Go 1.24 added `crypto/rand.Text` (proposal #67057): "a cryptographically
  random string using the standard RFC 4648 base32 alphabet … The result
  contains at least 128 bits of randomness … A future version may return
  longer texts as needed". In Go 1.27.3 it returns 26 characters
  ("⌈log₃₂ 2¹²⁸⌉ = 26 chars"), 130 bits, from `A-Z2-7`.

## Identifiable prefixes

- GitHub's token format (2021): prefixes `ghp_`, `gho_`, `ghu_`, `ghs_`,
  `ghr_`; "An underscore is not a Base64 character which helps ensure
  that our tokens cannot be accidentally duplicated"; "A 32 bit checksum
  in the last 6 digits of each token", "a CRC32 algorithm", encoded in
  Base62, so that GitHub can "eliminate fake tokens without having to hit
  our database". With the prefix alone it expected secret scanning's
  false positive rate "down to 0.5%".
- GitHub's partner program lists the properties of "high quality,
  identifiable secrets": "A uniquely defined prefix", "High entropy random
  strings", "A 32-bit checksum".
- None of the six open-source providers' generators read above adds a
  prefix or a checksum.
- Google: client secrets are widely reported to begin `GOCSPX-`, and
  GitHub secret scanning supports `google_oauth_client_secret`, but no
  Google document found states the format: **UNVERIFIED**. Microsoft
  Entra: GitHub secret scanning supports
  `azure_active_directory_application_secret`; a fixed marker such as
  `Q~` in Entra secrets is **UNVERIFIED**. Okta, Auth0 and Cognito: no
  prefix documented.

## What this means for pulsar

- **Generation.** The five open-source providers that generate secrets
  read them from a CSPRNG and encode them in a fixed alphabet; four of
  them also accept a secret the operator chose (Zitadel: UNVERIFIED), and
  Authelia accepts only the operator's. A 256-bit secret from `crypto/rand` is within what they
  do (Dex about 249 bits, Keycloak and node-oidc-provider 512).
  `crypto/rand.Text` alone gives 130 bits, below the README's 256.
- **Alphabet.** 32 bytes in unpadded base64url is 43 characters that
  form-encoding leaves unchanged, so a Client that skips the encoding
  still authenticates. The README's `openssl rand -base64 32` produces
  `+`, `/` and `=`, and a `+` breaks against such a Client.
- **Hash.** NIST SP 800-63B-4 §3.1.2.2 and ASVS 6.5.2 would accept a
  plain SHA-256 of a 256-bit secret; Argon2id is not required but is
  allowed, and keeps one format for passwords and secrets in the
  registry. Its cost is paid on every token request that authenticates
  with the secret, which bears on #35's cap on concurrent hashing.
  Zitadel and Hydra choose low work factors for generated secrets.
- **Parameters.** If Argon2id is kept, the README's t=2, m=32 MiB, p=1
  is above OWASP's second option (t=2, m=19 MiB, p=1); RFC 9106 §4
  recommends a 16-byte salt and a 32-byte tag, as C2SP's defaults do.
- **Output.** Authelia's command is the precedent: secret and digest on
  separate labeled lines, and a URL-encoded copy only when it differs.
- **Prefix.** No surveyed provider's source prefixes Client secrets. A
  prefix and checksum in GitHub's style would be pulsar's own choice,
  not an observed practice among OpenID Providers.
