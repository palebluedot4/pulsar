# Login throttling and concurrent password hashing

What the specifications in scope, security guidance and other providers
say about limiting online guessing of passwords and client secrets, and
about bounding the memory that concurrent Argon2id verifications take
(#35). Surveyed 2026-11-07 from specifications, official documentation and
official source code. Anything not confirmed is marked **UNVERIFIED**.

## Responses

- 429 (RFC 6585 §4): "the user has sent too many requests in a given amount
  of time"; it "MAY include a Retry-After header" and "MUST NOT be stored by
  a cache".
- 503 (RFC 9110 §15.6.4): "temporary overload"; "The server MAY send a
  Retry-After header field" (§10.2.3).
- RFC 6749 §5.2 defines no error code for a throttled or overloaded token
  endpoint. `temporarily_unavailable`, "The authorization server is
  currently unable to handle the request due to a temporary overloading",
  is defined for the authorization endpoint (§4.1.2.1), because a 503
  "cannot be returned … via an HTTP redirect", and the IANA OAuth
  Extensions Error Registry lists it for that endpoint only.
- Authelia answers a throttled token request 429 with `Retry-After` and
  `temporarily_unavailable`, with the comment that "OAuth 2.0 has no
  canonical rate-limit error code" (`internal/middlewares/const.go`).
  Auth0 answers 429 `too_many_attempts`; Ory Kratos answers a throttled
  login 429 `login_throttled` with `Retry-After`.

Sources: <https://www.rfc-editor.org/rfc/rfc6585#section-4>,
<https://www.rfc-editor.org/rfc/rfc9110#section-15.6.4>,
<https://www.iana.org/assignments/oauth-parameters/oauth-parameters.xhtml#extensions-error>.

## Concurrent hashing

Keycloak's `Argon2PasswordHashProviderFactory` creates a semaphore of as
many permits as there are CPU cores, with the comment that hashing more
values concurrently "only leads to an increased memory usage". It counts
hashes rather than weighing them by memory, and waits for a permit without
a limit; overload is shed separately, by `http-max-queued-requests`, with 503. Ory Kratos monitors the memory hashing takes and warns. No other
surveyed provider caps concurrent hashing.

`golang.org/x/sync/semaphore.Weighted` blocks in `Acquire` "until
resources are available or ctx is done". It serves waiters in order, so a
waiter whose weight does not fit holds back smaller ones behind it, and a
weight above the semaphore's size never fits. ASP.NET Core's concurrency
limiter rejects with 503 by default.

Sources: <https://pkg.go.dev/golang.org/x/sync/semaphore>,
<https://learn.microsoft.com/en-us/dotnet/api/microsoft.aspnetcore.ratelimiting.ratelimiteroptions.rejectionstatuscode>.

## Counting across replicas

`golang.org/x/time/rate` is a token bucket in one process; ASP.NET's
documentation warns that with per-instance limiters "the effective limit
is the configured limit multiplied by the number of instances". No
standard defines a limiter kept in PostgreSQL. Authelia counts failed
attempts newer than a window in a table; authentik upserts one row per
identifier and IP.

## Client addresses behind proxies

RFC 7239 §8.1: `Forwarded` "cannot be relied upon to be correct", and
before the first trusted proxy "the chain of IP addresses … cannot be
trusted". An address taken from `X-Forwarded-For` is safe only when added
by a proxy the server is configured to trust, read from the rightmost
entry. Keycloak (`proxy-trusted-addresses`) and authentik
(`listen.trusted_proxy_cidrs`) each have a setting for it.

Sources: <https://www.rfc-editor.org/rfc/rfc7239#section-8.1>,
<https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For>.

## Storing what is counted

Authelia and authentik store the identifier as it was typed. pulsar
departs from them: a username field sometimes receives a password typed
into the wrong field, and OWASP's Logging Cheat Sheet lists authentication
passwords among what must not be recorded. That is a principle applied
here, not a practice observed among the providers surveyed.

Source:
<https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html>.

## Conclusion

- Every provider that throttles counts per account; OWASP puts the count
  on the account because counts per IP fall to proxy networks. Counting
  per account is also the only measure that bounds the guesses at one
  End-User's password whatever the attacker's addresses, which RFC 6749
  §10.10 requires.
- RFC 6819, OWASP and Ory warn that lockout lets anyone lock out a known
  account; a delay that grows with each failure, as Ory and NIST's
  optional technique use, limits guessing without ending the account.
  Keycloak's and Ory's 15 minutes is the common upper bound.
- Throttled requests are refused before any hash runs, with 429 and
  `Retry-After`.
- A cap on concurrent hashing traces to no clause of RFC 6749, RFC 9700 or
  OpenID Connect; it is an availability control, backed by ASVS 15.1.3
  and libsodium's guidance, and Keycloak implements one.
- For a Client secret, RFC 6819 §4.3.5 lists high entropy, lockout and
  client assertions. A count per Client would let anyone who knows a
  client_id, which is public, hold up that Client; high entropy does not.
  §5.1.4.2.2 has the authorization server generate the secret, as Keycloak
  and Auth0 do (UNVERIFIED in this survey). pulsar's registry holds only
  hashes that an operator writes, so pulsar requires the entropy of the
  operator and cannot check it.
