# RFC 7009: OAuth 2.0 Token Revocation

Clauses of [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009) that pulsar,
as an authorization server, must or should meet. JSONP (§2.3) is not
offered, so its clauses are not listed. Nor is §2's "The authorization
server MUST use Transport Layer Security (TLS)": as for every endpoint,
TLS is the deployment's, served by pulsar when it is given a certificate
or by a proxy in front of it, and no test of pulsar's can show it.

## The endpoint (§2)

- REQ-REVOKE-1 (§2): "Implementations MUST support the revocation of
  refresh tokens and SHOULD support the revocation of access tokens (see
  Implementation Note)."

  pulsar revokes both. An access token is revoked by deleting its record,
  so UserInfo refuses it at once; a Resource Server that verifies the JWT
  itself, as RFC 9068 lets it, accepts it until it expires, at most ten
  minutes later, the case §3 describes for self-contained tokens.

- REQ-REVOKE-2 (§2): "The client requests the revocation of a particular
  token by making an HTTP POST request to the token revocation endpoint
  URL."

  The endpoint is `/revoke` under the issuer, and answers no other method
  but `OPTIONS`, for a preflight (REQ-REVOKE-13).

- REQ-REVOKE-3 (§2): "Since requests to the token revocation endpoint
  result in the transmission of plaintext credentials in the HTTP request,
  URLs for token revocation endpoints MUST be HTTPS URLs."

  Departure: as for every endpoint, an `http` issuer on a loopback host is
  accepted, and the revocation endpoint shares its scheme (REQ-DISC-1).

- REQ-REVOKE-15 (§2): "This URL MUST conform to the rules given in
  [RFC6749], Section 3.1."

  The URL is the issuer followed by `/revoke`, and the issuer has no query
  or fragment (REQ-DISC-1), so neither has the URL.

- REQ-REVOKE-16 (§2): "If the host of the token revocation endpoint can
  also be reached over HTTP, then the server SHOULD also offer a revocation
  service at the corresponding HTTP URI, but it MUST NOT publish this URI
  as a token revocation endpoint."

  Discovery publishes only the URL derived from the issuer, which is
  `https` but for the loopback departure of REQ-REVOKE-3. Departure: pulsar
  listens on one address, with TLS or without, so it offers no second
  revocation service over HTTP; whether the host can also be reached over
  HTTP is the deployment's choice.

## The request (§2.1)

- REQ-REVOKE-4 (§2.1, `token`): "REQUIRED. The token that the client wants
  to get revoked."

  A request without `token`, or that repeats a parameter (REQ-OAUTH-5),
  gets `invalid_request`, before the Client authenticates, so that a
  malformed request does not use up a client assertion.

- REQ-REVOKE-5 (§2.1, `token_type_hint`): "If the server is unable to
  locate the token using the given hint, it MUST extend its search across
  all of its supported token types."

  The hint orders the lookup only: `access_token` looks for an access
  token first, and `refresh_token` for a refresh token first. Without
  either, a token in the JWS compact serialization is looked for as an
  access token first, and any other as a refresh token first.

- REQ-REVOKE-6 (§2.1): "The client also includes its authentication
  credentials as described in Section 2.3. of [RFC6749]."

  A Client authenticates as at the token endpoint: by the one method it
  registered, a client assertion authenticating once, or, for a public
  Client, by its `client_id` alone (REQ-REVOKE-14). A Client that fails
  gets `invalid_client`.

- REQ-REVOKE-7 (§2.1): "The authorization server first validates the
  client credentials (in case of a confidential client) and then verifies
  whether the token was issued to the client making the revocation
  request. If this validation fails, the request is refused and the client
  is informed of the error by the authorization server as described
  below."

  A valid token that was issued to another Client is refused with 400 and
  `invalid_request`, and nothing is revoked. §2.1 names no error code;
  Keycloak, and node-oidc-provider for a confidential Client, answer this
  one ([research](../research/logout-revocation-resources.md#revocation)).
  The token is validated first, expiry included, as both of them do: one
  that is invalid gets 200 whichever Client presents it (REQ-REVOKE-10).

- REQ-REVOKE-8 (§2.1): "The invalidation takes place immediately, and the
  token cannot be used again after the revocation."

  A refresh token is refused, and an access token's record deleted, by the
  time the response is sent. A revocation and a refresh of one Refresh
  Token Family take turns, as a refresh token presented again and a
  refresh do (REQ-BCP-11).

- REQ-REVOKE-9 (§2.1): "If the particular token is a refresh token and
  the authorization server supports the revocation of access tokens, then
  the authorization server SHOULD also invalidate all access tokens based
  on the same authorization grant (see Implementation Note). If the token
  passed to the request is an access token, the server MAY revoke the
  respective refresh token as well."

  A refresh token, whichever of its family it is, used or not, revokes the
  whole Refresh Token Family and deletes the records of every access token
  issued from its code, as a refresh token presented again does. An access
  token revokes only itself, as Keycloak and Spring Authorization Server
  have it: its family's refresh token is still redeemed.

## The response (§2.2)

- REQ-REVOKE-10 (§2.2): "The authorization server responds with HTTP
  status code 200 if the token has been revoked successfully or if the
  client submitted an invalid token."

  The response has an empty body. A token pulsar cannot find, one of the
  Client's own already revoked, and one that is invalid, whichever Client
  presents it, all get 200. A refresh token is invalid
  once its Refresh Token Family has ended, whether or not the periodic
  deletion has removed it yet, so the answer does not depend on when that
  runs. An access token is invalid unless its signature verifies against
  the JWK Set and its claims pass the checks UserInfo applies: `iss`, `aud`,
  `exp`, `sub` and `jti` (REQ-AT-7, REQ-AT-8, REQ-AT-10).

- REQ-REVOKE-11 (§2.2): "An invalid token type hint value is ignored by
  the authorization server and does not influence the revocation
  response."

- REQ-REVOKE-12 (§2.2.1): "The error presentation conforms to the
  definition in Section 5.2 of [RFC6749]."

  Every error is the JSON object of RFC 6749 §5.2, with
  `Cache-Control: no-store`, as at the token endpoint. pulsar revokes both
  token types, so it never answers `unsupported_token_type`.

## Cross-origin requests (§2.3)

- REQ-REVOKE-13 (§2.3): "The revocation endpoint MAY support Cross-Origin
  Resource Sharing (CORS) [W3C.WD-cors-20120403] if it is aimed at use in
  combination with user-agent-based applications."

  It follows the token endpoint's policy (REQ-BROWSER-1): a preflight is
  approved for the origin of a public Client's redirect URI, and a request
  is answered with CORS headers when it comes from an origin of its own
  public Client. A request from any other origin gets `invalid_request`,
  and revokes nothing.

## Security considerations (§5)

- REQ-REVOKE-14 (§5): "According to this specification, a client's request
  must contain a valid client_id, in the case of a public client, or valid
  client credentials, in the case of a confidential client. The token
  being revoked must also belong to the requesting client."

- REQ-REVOKE-17 (§5): "Appropriate countermeasures, which should be in
  place for the token endpoint as well, MUST be applied to the revocation
  endpoint (see [RFC6819], Section 4.4.1.11). Specifically, invalid token
  type hints may misguide the authorization server and cause additional
  database lookups. Care MUST be taken to prevent malicious clients from
  exploiting this feature to launch denial-of-service attacks."

  A Client authenticates as at the token endpoint, with its
  countermeasures (REQ-OAUTH-44): each replica verifies a bounded number of
  secrets at once, answering 503 with `Retry-After` when it has no room,
  and failed attempts are not counted per Client, so that no one can hold
  up a Client's revocations. Nothing is looked up until the Client has
  authenticated, and a wrong hint costs at most one more lookup: one
  indexed query for a refresh token, or one signature verification for an
  access token.
