# RFC 7636: Proof Key for Code Exchange by OAuth Public Clients

Clauses of [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636) that pulsar,
as an authorization server, must meet, and three that bind the client but
that pulsar enforces (REQ-PKCE-6 to 8). pulsar requires PKCE of public
Clients only, and supports `S256` only (ADR 0002).

- REQ-PKCE-1 (§4.3, `code_challenge_method`): "OPTIONAL, defaults to
  "plain" if not present in the request."

  A `code_challenge` without a `code_challenge_method` is therefore a
  request for `plain`, and refused as REQ-PKCE-3 says.

- REQ-PKCE-2 (§4.4.1): "If the server requires Proof Key for Code Exchange
  (PKCE) by OAuth public clients and the client does not send the
  "code_challenge" in the request, the authorization endpoint MUST return
  the authorization error response with the "error" value set to
  "invalid_request"."

- REQ-PKCE-3 (§4.4.1): "If the server supporting PKCE does not support the
  requested transformation, the authorization endpoint MUST return the
  authorization error response with "error" value set to
  "invalid_request"."

  pulsar supports `S256` only, so `plain`, a method not sent, and any
  other method get `invalid_request`.

- REQ-PKCE-4 (§4.6): "If the values are not equal, an error response
  indicating "invalid_grant" as described in Section 5.2 of [RFC6749] MUST
  be returned."

- REQ-PKCE-5 (§4.4): "When the server issues the authorization code in the
  authorization response, it MUST associate the "code_challenge" and
  "code_challenge_method" values with the authorization code so it can be
  verified later."

  The challenge is stored with the code; the method, always `S256`, is
  not.

## Clauses that bind the client

RFC 7636 does not require an authorization server to check these, but two
widely deployed ones do, and pulsar makes the same checks:
[Keycloak](https://github.com/keycloak/keycloak/blob/30cf683465a1ddf7151462d7f480d6d17f986844/services/src/main/java/org/keycloak/protocol/oidc/utils/PkceUtils.java)
checks the form of a `code_verifier` and answers `invalid_grant`, and
[checks](https://github.com/keycloak/keycloak/blob/30cf683465a1ddf7151462d7f480d6d17f986844/services/src/main/java/org/keycloak/protocol/oidc/endpoints/AuthorizationEndpointChecker.java)
the form of a `code_challenge` with `invalid_request`;
[node-oidc-provider](https://github.com/panva/node-oidc-provider/blob/3ed87bef95d0f02b72917b9eb7d17ef5c3b2313b/lib/helpers/pkce_format.js)
checks both, answering `invalid_request` for each, and
[refuses](https://github.com/panva/node-oidc-provider/blob/3ed87bef95d0f02b72917b9eb7d17ef5c3b2313b/lib/actions/authorization/sender_constraints.js)
a `code_challenge_method` without a `code_challenge`.

- REQ-PKCE-6 (§4.1): "code-verifier = 43\*128unreserved"

  A `code_verifier` of any other form gets `invalid_grant`, as one that
  does not match does (REQ-PKCE-4) and as Keycloak answers, even if its
  challenge matches. The check bounds a verifier's length, not its
  entropy, which §7.1 leaves to the client.

- REQ-PKCE-7 (§4.2): "code-challenge = 43\*128unreserved"

  A `code_challenge` of any other form gets `invalid_request` at the
  authorization endpoint, before the End-User is asked to log in, rather
  than a code no verifier could redeem.

- REQ-PKCE-8 (§4.3, `code_challenge`): "REQUIRED. Code challenge."

  A request that sends `code_challenge_method` without `code_challenge`
  gets `invalid_request`, so that a Client that means to use PKCE is not
  issued a code without it.
