# RFC 6749: The OAuth 2.0 Authorization Framework

Clauses of [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) that pulsar,
as an authorization server, must or should meet.

## Refresh token (§1.5)

- REQ-OAUTH-30 (§1.5): "If the authorization server issues a refresh
  token, it is included when issuing an access token (i.e., step (D) in
  Figure 1)."

  pulsar issues one only for a code issued with offline access (OpenID
  Connect Core 1.0 §11, REQ-CORE-52), in the token response that redeems
  the code. The redemption starts a Refresh Token Family, which ends 30
  days later. Each token response that redeems one of the family's
  refresh tokens carries the next (REQ-BCP-9).

## Client authentication (§2.3)

- REQ-OAUTH-24 (§2.3): "The client MUST NOT use more than one
  authentication method in each request."

  A request that uses both HTTP Basic and the request body gets
  `invalid_request`, which §5.2 defines for a request that "utilizes more
  than one mechanism for authenticating the client". One that also
  carries an assertion gets `invalid_client` (REQ-ASSERT-2).

- REQ-OAUTH-3 (§2.3.1): "The authorization server MUST support the HTTP
  Basic authentication scheme for authenticating clients that were issued
  a client password."

  The client identifier and password are each form-encoded before Basic
  encoding, as §2.3.1 says, and are decoded the same way. A Client that
  registers `client_secret_basic` may authenticate by it alone.

- REQ-OAUTH-25 (§2.3.1): "The parameters can only be transmitted in the
  request-body and MUST NOT be included in the request URI."

  A Client that registers `client_secret_post` authenticates by
  `client_id` and `client_secret` in the request body. The token endpoint
  reads no parameter from the request URI, so credentials sent there
  authenticate nothing.

- REQ-OAUTH-44 (§2.3.1): "Since this client authentication method
  involves a password, the authorization server MUST protect any endpoint
  utilizing it against brute force attacks."

  A Client secret must be at least 256 bits from a cryptographically
  strong random source, as the README says, so that guessing one is as
  unlikely as guessing a code (REQ-OAUTH-21), as RFC 6819 §5.1.4.2.2
  advises; pulsar sees only its hash, so this rests on the operator. Each
  replica checks at most as many secrets and passwords at once as its
  memory cap allows
  ([ADR 0005](../adr/0005-guessing-throttled-per-account-by-delay.md)),
  which bounds how fast any can be guessed. A request refused for want of
  room gets 503 with `Retry-After`; §5.2 defines no error code for it, so
  the body borrows `temporarily_unavailable`, which §4.1.2.1 defines for
  the authorization endpoint. Attempts are not counted per Client, as
  logins are (REQ-OAUTH-45): a count kept by `client_id`, which is public,
  would let anyone hold up a Client's token requests, so a Client
  authenticates however many attempts have failed before.

- REQ-OAUTH-26 (§2.3.2): "When using other authentication methods, the
  authorization server MUST define a mapping between the client identifier
  (registration record) and authentication scheme."

  The registry is that mapping for every method: each Client registers
  one `token_endpoint_auth_method`, and authenticating by any other gets
  `invalid_client`, so that a weaker method cannot stand in for it.

## Authorization endpoint (§3.1)

- REQ-OAUTH-4 (§3.1): "The authorization server MUST ignore unrecognized
  request parameters."
- REQ-OAUTH-5 (§3.1): "Request and response parameters MUST NOT be included
  more than once."

  A repeated `client_id` or `redirect_uri` gets the error page, since
  neither can be trusted to redirect to; any other repeated parameter
  pulsar reads gets `invalid_request`, at either endpoint.

- REQ-OAUTH-6 (§3.1): "Parameters sent without a value MUST be treated as
  if they were omitted from the request."

## Redirection endpoint (§3.1.2)

- REQ-OAUTH-1 (§3.1.2): "The redirection endpoint URI MUST be an absolute
  URI as defined by [RFC3986] Section 4.3. ... The endpoint URI MUST NOT
  include a fragment component."

- REQ-OAUTH-2 (§3.1.2.2): "The authorization server SHOULD require all
  clients to register their redirection endpoint prior to utilizing the
  authorization endpoint."

## Token endpoint (§3.2)

- REQ-OAUTH-27 (§3.2.1): "Confidential clients or other clients issued
  client credentials MUST authenticate with the authorization server as
  described in Section 2.3 when making requests to the token endpoint."

  A Client registered for any method but `none` that sends only its
  `client_id` gets `invalid_client`.

## Authorization response (§4.1.2)

- REQ-OAUTH-7 (§4.1.2, `code`): "The authorization code MUST expire shortly
  after it is issued to mitigate the risk of leaks. A maximum authorization
  code lifetime of 10 minutes is RECOMMENDED."

  A code expires 60 seconds after it is issued.

- REQ-OAUTH-8 (§4.1.2, `code`): "The authorization code is bound to the
  client identifier and redirection URI."
- REQ-OAUTH-29 (§4.1.2, `code`): "If an authorization code is used more
  than once, the authorization server MUST deny the request and SHOULD
  revoke (when possible) all tokens previously issued based on that
  authorization code."

  The request gets `invalid_grant` (REQ-OAUTH-19), and the access tokens
  issued from the code are revoked, so that UserInfo refuses them. They are
  found by the code's hash, as the open-source providers surveyed find
  theirs by an identifier taken from the code
  ([research](../research/userinfo-and-claims.md#revoking-tokens-when-a-code-is-redeemed-twice)).
  A code issued with offline access started a Refresh Token Family, and
  every refresh token and access token of the family descends from the
  code, so the family is revoked too, as a reused refresh token revokes it
  (REQ-BCP-11), and so are the access tokens issued in it.

  They are revoked only when the request is otherwise valid: it
  authenticates as the code's Client, by that Client's registered method,
  and carries the code's redirect URI and, if the code was issued with a
  code challenge, a `code_verifier` that matches it, or, if not, no
  `code_verifier`. Any other request revokes nothing, whatever error it
  gets. This condition is not in
  RFC 6749. It is taken from OAuth 2.1 (draft-ietf-oauth-v2-1-17 §7.5.3,
  still a draft): "The authorization server SHOULD NOT revoke any issued
  tokens when receiving a replayed authorization code that contains invalid
  parameters", as Spring Authorization Server and node-oidc-provider do
  ([research](../research/refresh-tokens.md#a-reused-code-once-refresh-tokens-exist)).
  Before #49, any Client that presented the code revoked them; with
  Refresh Token Families lasting thirty days (#47), that would let anyone
  who has seen a code end an End-User's access with any Client. The code's
  own expiry is not one of the conditions: a valid request after the code
  has expired still revokes, for as long as the code's record is kept. A
  redeemed code's record is kept until the access token issued from it
  directly has expired, ten minutes after the redemption, and, if it
  started a Refresh Token Family, until the family ends, thirty days after
  the code was redeemed, as Spring Authorization Server and fosite keep
  theirs at least as long
  ([research](../research/refresh-tokens.md#a-reused-code-once-refresh-tokens-exist)).
  Once its tokens are revoked, it has none left to revoke, and is no longer
  kept. Its row records when it may be deleted, set as its state changes,
  and is deleted by the periodic deletion that next runs after that,
  which each replica runs every 15 minutes, as most providers
  surveyed decide from a time on the record
  ([research](../research/refresh-tokens.md#keeping-and-deleting-used-codes-used-refresh-tokens-and-grants)).
  So a valid replay revokes the family for as long as it lives. An access
  token the family issued in its last ten minutes outlives it, and a
  replay once the code's record is deleted does not revoke it: nothing
  then shows that a request's parameters are the code's, so it revokes
  nothing.

- REQ-OAUTH-9 (§4.1.2, `state`): "REQUIRED if the "state" parameter was
  present in the client authorization request. The exact value received
  from the client."

  pulsar returns `state` in error responses too, as §4.1.2.1 also
  requires.

- REQ-OAUTH-10 (§4.1.2.1): "If the request fails due to a missing, invalid,
  or mismatching redirection URI, or if the client identifier is missing or
  invalid, the authorization server SHOULD inform the resource owner of the
  error and MUST NOT automatically redirect the user-agent to the invalid
  redirection URI."

- REQ-OAUTH-22 (§4.1.2.1, `access_denied`): "The resource owner or
  authorization server denied the request."

  pulsar sends it when the End-User denies the request on the consent
  page, as OpenID Connect Core 1.0 §3.1.2.6 has an OP inform the Client.

- REQ-OAUTH-17 (§4.1.2.1, `unsupported_response_type`): "The authorization
  server does not support obtaining an authorization code using this
  method."
- REQ-OAUTH-18 (§4.1.2.1, `invalid_scope`): "The requested scope is
  invalid, unknown, or malformed."

## Access token request (§4.1.3)

- REQ-OAUTH-11 (§4.1.3): "ensure that the authorization code was issued to
  the authenticated confidential client, or if the client is public, ensure
  that the code was issued to "client_id" in the request"
- REQ-OAUTH-12 (§4.1.3): "ensure that the "redirect_uri" parameter is
  present if the "redirect_uri" parameter was included in the initial
  authorization request as described in Section 4.1.1, and if included
  ensure that their values are identical."
- REQ-OAUTH-43 (§4.1.3): "verify that the authorization code is valid,
  and"

  A code is valid only if pulsar issued it, it has neither expired nor been
  redeemed, and its End-User is still in the registry. A code for an
  End-User removed since it was issued gets `invalid_grant`
  (REQ-OAUTH-19) and is not used up, as a refresh token for them is
  refused (REQ-OAUTH-35). No specification says what a removal does to a
  grant, and the providers surveyed split two and two; pulsar refuses, as
  node-oidc-provider and Keycloak do
  ([research](../research/refresh-tokens.md#an-end-user-removed-after-a-grant)).

## Refreshing an access token (§6)

- REQ-OAUTH-33 (§6): "require client authentication for confidential
  clients or for any client that was issued client credentials (or with
  other authentication requirements),"

  A refresh request authenticates its Client as a code's redemption does:
  by the method the Client registered, or, for a public Client, by its
  `client_id` alone (REQ-OAUTH-27). A public Client that sends no
  `client_id` is not identified, and gets `invalid_client`.

- REQ-OAUTH-34 (§6): "authenticate the client if client authentication is
  included and ensure that the refresh token was issued to the
  authenticated client, and"

  A refresh token issued to another Client gets `invalid_grant`, however
  the Client authenticates, and stays redeemable by its own Client.

- REQ-OAUTH-35 (§6): "validate the refresh token."

  A refresh token is valid only if pulsar issued it, it has not been
  redeemed, its Refresh Token Family has neither ended nor been revoked,
  and the family's End-User is still in the registry. Any other gets
  `invalid_grant` (REQ-OAUTH-19). So removing an End-User from the
  registry ends every Client's offline access for them; adding them back
  restores it, since nothing is revoked. A Client removed from the
  registry cannot authenticate, and gets `invalid_client` (REQ-OAUTH-42).

- REQ-OAUTH-36 (§6, `scope`): "The requested scope MUST NOT include any
  scope not originally granted by the resource owner, and if omitted is
  treated as equal to the scope originally granted by the resource
  owner."

  A scope that includes any other value, even one pulsar does not support,
  gets `invalid_scope` (REQ-OAUTH-38), and the refresh token is not
  redeemed. A narrower scope issues an access token for that scope alone.
  The claims the authorization request's `claims` parameter asked for
  from UserInfo are not part of the scope: UserInfo returns them with
  every access token of the family, as it does with the one issued from
  the code, whatever its scope (REQ-CORE-43).

- REQ-OAUTH-37 (§6): "If a new refresh token is issued, the refresh token
  scope MUST be identical to that of the refresh token included by the
  client in the request."

  Every refresh token of a family is for the family's scope, whatever
  scope the request that issued it asked for.

## Token responses (§5)

- REQ-OAUTH-13 (§5.1): "The authorization server MUST include the HTTP
  "Cache-Control" response header field [RFC2616] with a value of
  "no-store" in any response containing tokens, credentials, or other
  sensitive information, as well as the "Pragma" response header field
  [RFC2616] with a value of "no-cache"."

  pulsar sends both on every token endpoint response, errors included.

- REQ-OAUTH-14 (§5.2, `invalid_client`): "If the client attempted to
  authenticate via the "Authorization" request header field, the
  authorization server MUST respond with an HTTP 401 (Unauthorized) status
  code and include the "WWW-Authenticate" response header field matching
  the authentication scheme used by the client."

  pulsar answers every `invalid_client` this way, naming the Basic scheme
  even to a Client that sent no `Authorization` header, which §5.2 allows.

- REQ-OAUTH-42 (§5.2, `invalid_client`): "Client authentication failed
  (e.g., unknown client, no client authentication included, or unsupported
  authentication method)."

  A Client removed from the registry is unknown, so its token requests
  get `invalid_client`, a refresh among them. #53 asked for
  `invalid_grant` there; the Client cannot authenticate, and §5.2 names
  this error for it.

- REQ-OAUTH-15 (§5.2): "The authorization server responds with an HTTP 400
  (Bad Request) status code (unless specified otherwise) and includes the
  following parameters with the response:"

  pulsar sends them as a JSON object, as §5.2 goes on to say. A failure of
  pulsar's own, such as a database error, is answered with 500 and
  `server_error`, a code §5.2 does not define, since none of its codes
  describes it.

- REQ-OAUTH-19 (§5.2, `invalid_grant`): "The provided authorization grant
  (e.g., authorization code, resource owner credentials) or refresh token
  is invalid, expired, revoked, does not match the redirection URI used in
  the authorization request, or was issued to another client."
- REQ-OAUTH-20 (§5.2, `unsupported_grant_type`): "The authorization grant
  type is not supported by the authorization server."

  pulsar supports `authorization_code` and `refresh_token`.

- REQ-OAUTH-38 (§5.2, `invalid_scope`): "The requested scope is invalid,
  unknown, malformed, or exceeds the scope granted by the resource owner."

## Security considerations (§10)

- REQ-OAUTH-28 (§10.2): "The authorization server SHOULD NOT process
  repeated authorization requests automatically (without active resource
  owner interaction) without authenticating the client or relying on other
  measures to ensure that the repeated request comes from the original
  client and not an impersonator."

  A public Client cannot authenticate, and pulsar takes no other measure
  as proof of its identity, so its requests are processed as if no request
  had been approved before (RFC 8252 §8.6): the consent page is shown
  every time, and `prompt=none` gets `consent_required`. RFC 8252 §8.6
  allows claimed `https` redirect URIs to count as proof; pulsar does not
  count them.

- REQ-OAUTH-31 (§10.4): "Refresh tokens MUST be kept confidential in
  transit and storage, and shared only among the authorization server and
  the client to whom the refresh tokens were issued."

  pulsar stores only each refresh token's SHA-256, as it stores codes, so
  that a copy of the database holds none a Client could redeem.

- REQ-OAUTH-32 (§10.4): "The authorization server MUST maintain the
  binding between a refresh token and the client to whom it was issued."

  Each refresh token belongs to a Refresh Token Family, which records the
  Client its code was issued to.

- REQ-OAUTH-39 (§10.4): "The authorization server MUST verify the binding
  between the refresh token and client identity whenever the client
  identity can be authenticated."

  pulsar verifies it on every refresh request, against the Client that
  authenticated or, for a public Client, the one its `client_id` names.

- REQ-OAUTH-40 (§10.4): "When client authentication is not possible, the
  authorization server SHOULD deploy other means to detect refresh token
  abuse."

  pulsar rotates every Client's refresh tokens, as §10.4 goes on to
  suggest: each is redeemed once, and its redemption issues the next
  (REQ-BCP-9).

- REQ-OAUTH-41 (§10.4): "The authorization server MUST ensure that refresh
  tokens cannot be generated, modified, or guessed to produce valid
  refresh tokens by unauthorized parties."

  A refresh token is 256 bits from `crypto/rand` with no structure, and is
  valid only if its hash is recorded, so none can be made or changed into
  another; guessing one is as unlikely as guessing a code (REQ-OAUTH-21).

- REQ-OAUTH-16 (§10.5): "Authorization codes MUST be short lived and
  single-use."
- REQ-OAUTH-45 (§10.10): "The authorization server MUST prevent attackers
  from guessing access tokens, authorization codes, refresh tokens,
  resource owner passwords, and client credentials."

  Tokens and codes are too long to guess (REQ-OAUTH-21), and so are Client
  secrets (REQ-OAUTH-44). Passwords are chosen by people, so the attempts
  to sign in are counted: per End-User, and per username no End-User has.
  After five attempts without a success, each further one must wait a
  second, doubling with each attempt up to fifteen minutes; one that comes
  sooner gets 429 with `Retry-After`, before the password is checked, even
  if it is right. A success clears the count, and a day without an attempt
  forgets it
  ([ADR 0005](../adr/0005-guessing-throttled-per-account-by-delay.md)).

- REQ-OAUTH-21 (§10.10): "The probability of an attacker guessing generated
  tokens (and other credentials not intended for handling by end-users)
  MUST be less than or equal to 2^(-128) and SHOULD be less than or equal
  to 2^(-160)."

  A code is 256 bits from `crypto/rand`, and so is a refresh token. Tests
  check their size; that the bits are random rests on `crypto/rand`.

- REQ-OAUTH-23 (§10.12): "The authorization server MUST implement CSRF
  protection for its authorization endpoint and ensure that a malicious
  client cannot obtain authorization without the awareness and explicit
  consent of the resource owner."

  Authorization comes from the consent form, which refuses cross-origin
  submissions. A decision counts only for the request it was made for, in
  the Login Session of the browser that made it; nothing in an
  authorization request's own parameters can stand in for it.
