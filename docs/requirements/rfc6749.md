# RFC 6749: The OAuth 2.0 Authorization Framework

Clauses of [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749) that pulsar,
as an authorization server, must or should meet.

## Client authentication (§2.3)

- REQ-OAUTH-24 (§2.3): "The client MUST NOT use more than one
  authentication method in each request."

  A request that uses both HTTP Basic and the request body gets
  `invalid_request`, which §5.2 defines for a request that "utilizes more
  than one mechanism for authenticating the client". One that also
  carries an assertion gets `invalid_client` (REQ-ASSERT-2).

- REQ-OAUTH-3 (§2.3.1): "The authorization server MUST support the HTTP
  Basic authentication scheme for authenticating clients that were issued
  a client password."

  The client identifier and password are each form-encoded before Basic
  encoding, as §2.3.1 says, and are decoded the same way. A Client that
  registers `client_secret_basic` may authenticate by it alone.

- REQ-OAUTH-25 (§2.3.1): "The parameters can only be transmitted in the
  request-body and MUST NOT be included in the request URI."

  A Client that registers `client_secret_post` authenticates by
  `client_id` and `client_secret` in the request body. The token endpoint
  reads no parameter from the request URI, so credentials sent there
  authenticate nothing.

- REQ-OAUTH-26 (§2.3.2): "When using other authentication methods, the
  authorization server MUST define a mapping between the client identifier
  (registration record) and authentication scheme."

  The registry is that mapping for every method: each Client registers
  one `token_endpoint_auth_method`, and authenticating by any other gets
  `invalid_client`, so that a weaker method cannot stand in for it.

## Authorization endpoint (§3.1)

- REQ-OAUTH-4 (§3.1): "The authorization server MUST ignore unrecognized
  request parameters."
- REQ-OAUTH-5 (§3.1): "Request and response parameters MUST NOT be included
  more than once."

  A repeated `client_id` or `redirect_uri` gets the error page, since
  neither can be trusted to redirect to; any other repeated parameter
  pulsar reads gets `invalid_request`, at either endpoint.

- REQ-OAUTH-6 (§3.1): "Parameters sent without a value MUST be treated as
  if they were omitted from the request."

## Redirection endpoint (§3.1.2)

- REQ-OAUTH-1 (§3.1.2): "The redirection endpoint URI MUST be an absolute
  URI as defined by [RFC3986] Section 4.3. ... The endpoint URI MUST NOT
  include a fragment component."

- REQ-OAUTH-2 (§3.1.2.2): "The authorization server SHOULD require all
  clients to register their redirection endpoint prior to utilizing the
  authorization endpoint."

## Token endpoint (§3.2)

- REQ-OAUTH-27 (§3.2.1): "Confidential clients or other clients issued
  client credentials MUST authenticate with the authorization server as
  described in Section 2.3 when making requests to the token endpoint."

  A Client registered for any method but `none` that sends only its
  `client_id` gets `invalid_client`.

## Authorization response (§4.1.2)

- REQ-OAUTH-7 (§4.1.2, `code`): "The authorization code MUST expire shortly
  after it is issued to mitigate the risk of leaks. A maximum authorization
  code lifetime of 10 minutes is RECOMMENDED."

  A code expires 60 seconds after it is issued.

- REQ-OAUTH-8 (§4.1.2, `code`): "The authorization code is bound to the
  client identifier and redirection URI."
- REQ-OAUTH-29 (§4.1.2, `code`): "If an authorization code is used more
  than once, the authorization server MUST deny the request and SHOULD
  revoke (when possible) all tokens previously issued based on that
  authorization code."

  The request gets `invalid_grant` (REQ-OAUTH-19), and the access tokens
  issued from the code are revoked, so that UserInfo refuses them. Any
  Client that presents the code revokes them, and they are revoked until
  they expire, even after the code has.

- REQ-OAUTH-9 (§4.1.2, `state`): "REQUIRED if the "state" parameter was
  present in the client authorization request. The exact value received
  from the client."

  pulsar returns `state` in error responses too, as §4.1.2.1 also
  requires.

- REQ-OAUTH-10 (§4.1.2.1): "If the request fails due to a missing, invalid,
  or mismatching redirection URI, or if the client identifier is missing or
  invalid, the authorization server SHOULD inform the resource owner of the
  error and MUST NOT automatically redirect the user-agent to the invalid
  redirection URI."

- REQ-OAUTH-22 (§4.1.2.1, `access_denied`): "The resource owner or
  authorization server denied the request."

  pulsar sends it when the End-User denies the request on the consent
  page, as OpenID Connect Core 1.0 §3.1.2.6 has an OP inform the Client.

- REQ-OAUTH-17 (§4.1.2.1, `unsupported_response_type`): "The authorization
  server does not support obtaining an authorization code using this
  method."
- REQ-OAUTH-18 (§4.1.2.1, `invalid_scope`): "The requested scope is
  invalid, unknown, or malformed."

## Access token request (§4.1.3)

- REQ-OAUTH-11 (§4.1.3): "ensure that the authorization code was issued to
  the authenticated confidential client, or if the client is public, ensure
  that the code was issued to "client_id" in the request"
- REQ-OAUTH-12 (§4.1.3): "ensure that the "redirect_uri" parameter is
  present if the "redirect_uri" parameter was included in the initial
  authorization request as described in Section 4.1.1, and if included
  ensure that their values are identical."

## Token responses (§5)

- REQ-OAUTH-13 (§5.1): "The authorization server MUST include the HTTP
  "Cache-Control" response header field [RFC2616] with a value of
  "no-store" in any response containing tokens, credentials, or other
  sensitive information, as well as the "Pragma" response header field
  [RFC2616] with a value of "no-cache"."

  pulsar sends both on every token endpoint response, errors included.

- REQ-OAUTH-14 (§5.2, `invalid_client`): "If the client attempted to
  authenticate via the "Authorization" request header field, the
  authorization server MUST respond with an HTTP 401 (Unauthorized) status
  code and include the "WWW-Authenticate" response header field matching
  the authentication scheme used by the client."

  pulsar answers every `invalid_client` this way, naming the Basic scheme
  even to a Client that sent no `Authorization` header, which §5.2 allows.

- REQ-OAUTH-15 (§5.2): "The authorization server responds with an HTTP 400
  (Bad Request) status code (unless specified otherwise) and includes the
  following parameters with the response:"

  pulsar sends them as a JSON object, as §5.2 goes on to say. A failure of
  pulsar's own, such as a database error, is answered with 500 and
  `server_error`, a code §5.2 does not define, since none of its codes
  describes it.

- REQ-OAUTH-19 (§5.2, `invalid_grant`): "The provided authorization grant
  (e.g., authorization code, resource owner credentials) or refresh token
  is invalid, expired, revoked, does not match the redirection URI used in
  the authorization request, or was issued to another client."
- REQ-OAUTH-20 (§5.2, `unsupported_grant_type`): "The authorization grant
  type is not supported by the authorization server."

## Security considerations (§10)

- REQ-OAUTH-28 (§10.2): "The authorization server SHOULD NOT process
  repeated authorization requests automatically (without active resource
  owner interaction) without authenticating the client or relying on other
  measures to ensure that the repeated request comes from the original
  client and not an impersonator."

  A public Client cannot authenticate, and pulsar takes no other measure
  as proof of its identity, so its requests are processed as if no request
  had been approved before (RFC 8252 §8.6): the consent page is shown
  every time, and `prompt=none` gets `consent_required`. RFC 8252 §8.6
  allows claimed `https` redirect URIs to count as proof; pulsar does not
  count them.

- REQ-OAUTH-16 (§10.5): "Authorization codes MUST be short lived and
  single-use."
- REQ-OAUTH-21 (§10.10): "The probability of an attacker guessing generated
  tokens (and other credentials not intended for handling by end-users)
  MUST be less than or equal to 2^(-128) and SHOULD be less than or equal
  to 2^(-160)."

  A code is 256 bits from `crypto/rand`. A test checks its size; that the
  bits are random rests on `crypto/rand`.

- REQ-OAUTH-23 (§10.12): "The authorization server MUST implement CSRF
  protection for its authorization endpoint and ensure that a malicious
  client cannot obtain authorization without the awareness and explicit
  consent of the resource owner."

  Authorization comes from the consent form, which refuses cross-origin
  submissions. A decision counts only for the request it was made for, in
  the Login Session of the browser that made it; nothing in an
  authorization request's own parameters can stand in for it.
