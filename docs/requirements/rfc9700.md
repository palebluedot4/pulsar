# RFC 9700: Best Current Practice for OAuth 2.0 Security

Clauses of [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700) that apply to
pulsar's authorization code flow and its client credentials grant.

- REQ-BCP-1 (§2.1.1): "Authorization servers MUST provide a way to detect
  their support for PKCE. It is RECOMMENDED for authorization servers to
  publish the element code_challenge_methods_supported in their
  Authorization Server Metadata [RFC8414] containing the supported PKCE
  challenge methods (which can be used by the client to detect PKCE
  support)."

- REQ-BCP-2 (§4.16): "Authorization servers MUST prevent clickjacking
  attacks. Multiple countermeasures are described in [RFC6819], including
  the use of the X-Frame-Options HTTP response header field and
  frame-busting JavaScript. In addition to those, authorization servers
  SHOULD also use Content Security Policy (CSP) level 2 [W3C.CSP-2] or
  greater."

- REQ-BCP-3 (§2.1): "When comparing client redirection URIs against
  pre-registered URIs, authorization servers MUST utilize exact string
  matching except for port numbers in localhost redirection URIs of native
  apps (see Section 4.1.3)."

  pulsar makes the exception for the port of a public Client's loopback IP
  redirect URI, which RFC 8252 §7.3 requires (REQ-NATIVE-1), and for no
  other: not for
  a URI whose host is `localhost`, which RFC 8252 §8.3 does not
  recommend.

- REQ-BCP-4 (§4.12): "Authorization servers that redirect a request that
  potentially contains the user's credentials therefore MUST NOT use the
  HTTP 307 status code for redirection. If an HTTP redirection (and not,
  for example, JavaScript) is used for such a request, the authorization
  server SHOULD use HTTP status code 303 (See Other)."

  pulsar answers with 303 from the login form, which carries a password,
  and from the authorization endpoint, which a Client may send by POST.

- REQ-BCP-5 (§2.1.1): "Authorization servers MUST support PKCE
  [RFC7636]."

- REQ-BCP-6 (§2.1.1): "If a client sends a valid PKCE code_challenge
  parameter in the authorization request, the authorization server MUST
  enforce the correct usage of code_verifier at the token endpoint."

  A Client of any type, public or confidential, that sends a
  `code_challenge` must redeem the code with its verifier.

- REQ-BCP-7 (§2.1.1): "Authorization servers MUST mitigate PKCE downgrade
  attacks by ensuring that a token request containing a code_verifier
  parameter is accepted only if a code_challenge parameter was present in
  the authorization request; see Section 4.8.2 for details."

  Such a request gets `invalid_grant`, as one whose verifier does not
  match does.

- REQ-BCP-12 (§2.6): "However, CORS MUST NOT be supported at the
  authorization endpoint, as the client does not access this endpoint
  directly; instead, the client redirects the user agent to it."

  §2.6 says the token endpoint, the metadata endpoint and the `jwks_uri`
  endpoint "MAY support" CORS; pulsar's do, as REQ-BROWSER-1 requires.

## Access token privilege restriction (§2.3)

- REQ-BCP-14 (§2.3): "The privileges associated with an access token
  SHOULD be restricted to the minimum required for the particular
  application or use case."

  An access token for a Resource Server holds only that Resource Server's
  scopes, of those granted (REQ-RESOURCE-7).

- REQ-BCP-15 (§2.3): "In particular, access tokens SHOULD be
  audience-restricted to a specific resource server or, if that is not
  feasible, to a small set of resource servers."

  Every access token's `aud` names one recipient: the Resource Server the
  `resource` parameter names, or, without one, pulsar's issuer, for
  UserInfo (REQ-AT-5, REQ-AT-12). No Resource Server may have the issuer
  as its identifier, so the two never coincide. §2.3's MUST, to refuse an
  access token meant for another resource server, falls on each Resource
  Server; pulsar meets it at UserInfo (REQ-AT-8).

## Client authentication (§2.5)

- REQ-BCP-16 (§2.5): "It is RECOMMENDED to use asymmetric cryptography for
  client authentication, such as mutual TLS for OAuth 2.0 [RFC8705] or
  signed JWTs ("Private Key JWT") in accordance with [RFC7521] and
  [RFC7523]."

  Every confidential Client may register `private_key_jwt`, a machine
  Client included, and the README recommends it for machine Clients. pulsar
  does not support mutual TLS.

## Client impersonating resource owner (§4.15.1)

- REQ-BCP-17 (§4.15.1): "Authorization servers SHOULD NOT allow clients to
  influence their client_id or any other claim that could cause confusion
  with a genuine resource owner if a common namespace for client IDs and
  user identifiers exists, such as in the sub claim example from [RFC9068]
  shown in Section 4.15 above. Where this cannot be avoided, authorization
  servers MUST provide other means for the resource server to distinguish
  between the two types of access tokens."

  A machine Client's access token has its `client_id` as `sub`
  (REQ-AT-15), so the two share a namespace. Clients do not influence their
  `client_id`, which the operator registers
  ([ADR 0001](../adr/0001-clients-and-end-users-from-a-static-file.md)).
  The registry accepts an End-User's Subject only as a lowercase UUID, and
  pulsar refuses to start on any Client whose `client_id` is a UUID, in
  any case, a Client of the code flow included, whose `client_id` would
  otherwise appear beside an End-User's `sub` in their access tokens. So a
  Resource Server tells the two apart by `sub` alone: equal to `client_id`
  for a machine Client, a UUID for an End-User. This also meets RFC 9068
  §5: authorization servers "should prevent scenarios where clients can
  affect the value of the "sub" claim in ways that could confuse resource
  servers", a sentence with no BCP 14 keyword, and so with no ID of its own
  ([ADR 0007](../adr/0007-a-machine-clients-sub-is-its-client-id.md)).

## Refresh tokens (§4.14.2)

- REQ-BCP-8 (§4.14.2): "If refresh tokens are issued, those refresh tokens
  MUST be bound to the scope and resource servers as consented by the
  resource owner."

  A Refresh Token Family records the scope the End-User allowed, and no
  refresh issues an access token for more (REQ-OAUTH-36). It records the
  Resource Server its code was issued for, if any, and every access token
  it issues is for that Resource Server, or, if none, for pulsar alone, the
  default resource (REQ-AT-5); a refresh that names another gets
  `invalid_target` (REQ-RESOURCE-6).

- REQ-BCP-9 (§4.14.2, refresh token rotation): "the authorization server
  issues a new refresh token with every access token refresh response.
  The previous refresh token is invalidated, but information about the
  relationship is retained by the authorization server."

  pulsar rotates the refresh tokens of every Client, public or
  confidential, since it supports neither of the sender-constraining
  methods §4.14.2 offers instead. A refresh token redeemed once is
  refused after that, and its record is kept in its family until the
  family ends, revoked or not, when the family and its refresh tokens are
  deleted, by the periodic deletion that next runs, which each replica
  runs every 15 minutes. Of two
  redemptions at once, at most one succeeds: the database marks the
  refresh token used in the transaction that records its replacement, so
  this holds across replicas too, and the other is taken as a refresh
  token presented again (REQ-BCP-11).

- REQ-BCP-11 (§4.14.2, refresh token rotation): "If a refresh token is
  compromised and subsequently used by both the attacker and the
  legitimate client, one of them will present an invalidated refresh
  token, which will inform the authorization server of the breach. The
  authorization server cannot determine which party submitted the invalid
  refresh token, but it will revoke the active refresh token."

  A refresh token already redeemed, presented again by the Client it was
  issued to while its Refresh Token Family lives, gets `invalid_grant`
  (REQ-OAUTH-19), and the whole family is revoked: each of its refresh
  tokens, the active one included, is refused from then on, and the
  access tokens issued in it, the one issued from its code included, are
  revoked too, so that UserInfo refuses them at once rather than when
  they expire. A refresh that commits while the family is being revoked
  is waited for, so its access token is revoked too, and one that starts
  after finds the family revoked. Once the family has ended, a refresh
  token of it presented again is refused and revokes nothing: no refresh
  token of the family can be redeemed by then, but an access token it
  issued in its last ten minutes lives on until it expires.

  A refresh token presented by another Client gets `invalid_grant` and
  revokes nothing, as a code replayed by another Client revokes nothing
  (REQ-OAUTH-29), so that one who has only seen a refresh token cannot end
  the End-User's offline access with another Client. No specification in
  scope says whether such a reuse should revoke. Of the providers surveyed
  that detect a reuse, node-oidc-provider and Keycloak check the Client
  first and revoke nothing, as pulsar does; fosite alone revokes for any
  Client that authenticates
  ([research](../research/refresh-tokens.md#a-refresh-token-presented-again)).
  §4.14.2 describes the attacker
  using the token as the legitimate client does: for a confidential
  Client, that takes its credentials; for a public Client, which has none,
  its `client_id` alone, and then the family is revoked.

  Departure: there is no grace period. Some providers accept a refresh
  token presented again shortly after it was redeemed, so that a Client
  whose refresh response was lost in transit can retry; pulsar takes
  §4.14.2 literally, and any second presentation revokes the family. The
  cost is that such a Client revokes its own family, and the End-User
  must be sent through authorization again, signing in if their Login
  Session has ended.

- REQ-BCP-10 (§4.14.2): "Refresh tokens SHOULD expire if the client has
  been inactive for some time, i.e., the refresh token has not been used
  to obtain fresh access tokens for some time."

  Departure: a Refresh Token Family has no limit for inactivity. It ends
  30 days after its code is redeemed, however recently or long ago its
  Client last refreshed. #47 leaves an inactivity limit out of scope.

- REQ-BCP-13 (§4.14.2): "Authorization servers MAY revoke refresh tokens
  automatically in case of a security event, such as: password change or
  logout at the authorization server."

  Logout at pulsar (RP-Initiated Logout) ends the Login Session alone. It
  revokes no Refresh Token Family and deletes no access token: pulsar
  issues refresh tokens only for offline access, which is meant to
  outlast the session; an access token expires within ten minutes; and
  all four providers surveyed keep offline tokens through logout
  ([research](../research/logout-revocation-resources.md#logout-and-refresh-tokens)).

  Departure: OAuth 2.1 (draft-ietf-oauth-v2-1-17) §9.3.2 says
  "Authorization servers SHOULD link the lifetime of the refresh token to
  the user's authenticated session with the authorization server, so that
  when the user logs out, previously issued refresh tokens become
  invalid", for browser-based applications. pulsar does not: OAuth 2.1 is
  still a draft, none of the four providers surveyed does it by default,
  and a public Client's refresh token survives logout as a confidential
  Client's does.
