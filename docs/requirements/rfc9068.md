# RFC 9068: JSON Web Token (JWT) Profile for OAuth 2.0 Access Tokens

Clauses of [RFC 9068](https://www.rfc-editor.org/rfc/rfc9068) that pulsar,
as an authorization server issuing JWT access tokens, must or should meet.

- REQ-AT-1 (§2.1): "JWT access tokens MUST be signed. [...] JWT access
  tokens MUST NOT use "none" as the signing algorithm."
- REQ-AT-2 (§2.1): "JWT access tokens MUST include this media type in the
  "typ" header parameter to explicitly declare that the JWT represents an
  access token complying with this profile. Per the definition of "typ" in
  Section 4.1.9 of [RFC7515], it is RECOMMENDED that the "application/"
  prefix be omitted. Therefore, the "typ" value used SHOULD be "at+jwt"."
- REQ-AT-3 (§2.2): "iss REQUIRED [...] exp REQUIRED [...] aud REQUIRED
  [...] sub REQUIRED [...] client_id REQUIRED [...] iat REQUIRED [...] jti
  REQUIRED"
- REQ-AT-4 (§2.2.3): "If an authorization request includes a scope
  parameter, the corresponding issued JWT access token SHOULD include a
  "scope" claim as defined in Section 4.2 of [RFC8693]."
- REQ-AT-5 (§3): "If the request does not include a "resource" parameter,
  the authorization server MUST use a default resource indicator in the
  "aud" claim."

  The default is the issuer: such an access token is for pulsar's
  UserInfo. pulsar refuses to start on a Resource Server whose identifier
  is the issuer, compared as UserInfo compares `aud`, as a string, so that
  only UserInfo's access tokens name it. This MUST governs the `aud` of an
  access token issued; the `client_credentials` grant issues none without
  `resource`, which it refuses with `invalid_target` (REQ-RESOURCE-10).

- REQ-AT-15 (§2.2, `sub`): "In cases of access tokens obtained through
  grants where no resource owner is involved, such as the client
  credentials grant, the value of "sub" SHOULD correspond to an identifier
  the authorization server uses to indicate the client application."

  A machine Client's access token has its `client_id` as `sub`, as
  node-oidc-provider, Ory Hydra and Spring Authorization Server have it
  ([ADR 0007](../adr/0007-a-machine-clients-sub-is-its-client-id.md)).

## Resource Servers (§3)

- REQ-AT-12 (§3): "If the request includes a "resource" parameter (as
  defined in [RFC8707]), the resulting JWT access token "aud" claim SHOULD
  have the same value as the "resource" parameter in the request."

  The `aud` is the Resource Server's identifier, a string, which the
  `resource` parameter equals exactly (REQ-RESOURCE-4).

- REQ-AT-13 (§3): "The authorization server MUST NOT issue a JWT access
  token if the authorization granted by the token would be ambiguous."

  §5 describes the ambiguity: several audiences whose scopes cannot be told
  apart. An access token's `aud` names one recipient, and its `scope`
  holds only that recipient's scopes: OpenID Connect's for the issuer, or
  the Resource Server's own, which the registry keeps apart from OpenID
  Connect's and from every other Resource Server's.

- REQ-AT-14 (§3): "If a "scope" parameter is present in the request, the
  authorization server SHOULD use it to infer the value of the default
  resource indicator to be used in the "aud" claim. [...] If the values in
  the "scope" parameter refer to different default resource indicator
  values, the authorization server SHOULD reject the request with
  "invalid_scope" as described in Section 4.1.2.1 of [RFC6749]."

  Departure: pulsar does not infer a Resource Server from `scope`. Without
  `resource`, the default is always the issuer, and a Resource Server's
  scope is ignored, as a scope pulsar does not know is (RFC 6749 §3.3),
  rather than refused with `invalid_scope` beside `openid`, which every
  request carries and which is the issuer's. So a request without
  `resource` is answered as it was before Resource Servers were
  registered, as #70 decides. node-oidc-provider likewise answers a
  request without `resource`, with `openid` in `scope`, with an access
  token for its UserInfo
  ([research](../research/logout-revocation-resources.md#resource-handling)).
  The `client_credentials` grant has no default to infer: it issues no
  access token without `resource` (REQ-AT-5).

## Validation at UserInfo (§4)

pulsar validates the access tokens it issued, at its own UserInfo
endpoint, as a resource server must.

- REQ-AT-6 (§4): "The resource server MUST verify that the "typ" header
  value is "at+jwt" or "application/at+jwt" and reject tokens carrying any
  other value."

  The value is compared without regard to case, as RFC 7515 §4.1.9 says
  media type values are.

- REQ-AT-7 (§4): "The issuer identifier for the authorization server
  (which is typically obtained during discovery) MUST exactly match the
  value of the "iss" claim."
- REQ-AT-8 (§4): "The JWT access token MUST be rejected if "aud" does not
  contain a resource indicator of the current resource server as a valid
  audience."

  UserInfo's resource indicator is the issuer, the default audience
  (REQ-AT-5), so it refuses an access token for a Resource Server.

- REQ-AT-9 (§4): "The resource server MUST validate the signature of all
  incoming JWT access tokens according to [RFC7515] using the algorithm
  specified in the JWT "alg" Header Parameter. The resource server MUST
  reject any JWT in which the value of "alg" is "none". The resource server
  MUST use the keys provided by the authorization server."

  Only RS256 is accepted, with the key of the JWK Set that the `kid` names.

- REQ-AT-10 (§4): "The current time MUST be before the time represented by
  the "exp" claim."

  pulsar allows no leeway: it validates against its own clock.

- REQ-AT-11 (§4): "In particular, in case of any failure in the validation
  checks listed above, the authorization server response MUST include the
  error code "invalid_token"."
