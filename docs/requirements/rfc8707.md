# RFC 8707: Resource Indicators for OAuth 2.0

Clauses of [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707) that pulsar,
as an authorization server, must or should meet. A Client names a Resource
Server registered for it by the `resource` parameter, at the authorization
endpoint and the token endpoint; the evidence is in
[the research](../research/logout-revocation-resources.md#resource-indicators-and-audience-restriction).

## The parameter (§2)

- REQ-RESOURCE-1 (§2): "Its value MUST be an absolute URI, as specified by
  Section 4.3 of [RFC3986]. The URI MUST NOT include a fragment
  component."

  pulsar refuses to start on a Resource Server whose identifier is not
  one, and compares a request's `resource` with the identifiers
  registered as strings, exactly, so a value that is not one matches none
  and is refused (REQ-RESOURCE-4). An identifier may have a query: §2 says
  the parameter "SHOULD NOT include a query component, but it is
  recognized that there are cases that make a query component a useful
  and necessary part of the resource parameter".

- REQ-RESOURCE-2 (§2): "The following error code is provided for an
  authorization server to indicate problems with the requested
  resource(s) in response to an authorization request or access token
  request. It can also be used to inform the client that it has requested
  an invalid combination of resource and scope. invalid_target The
  requested resource is invalid, missing, unknown, or malformed."

  At the authorization endpoint, the error goes to the redirect URI by the
  Response Mode requested, as every other error does once the Client and
  redirect URI are known; at the token endpoint, in the JSON form of
  RFC 6749 §5.2. An invalid combination is a request whose scope, once
  the scopes pulsar ignores are left out, holds none of the Resource
  Server's scopes: an access token for a Resource Server always allows at
  least one of them, so the registry requires each to have one.

- REQ-RESOURCE-3 (§2): "The authorization server SHOULD audience-restrict
  issued access tokens to the resource(s) indicated by the "resource"
  parameter."

  The access token's `aud` is the Resource Server's identifier, alone
  (REQ-AT-12).

## The authorization request (§2.1)

- REQ-RESOURCE-4 (§2.1): "If the authorization server fails to parse the
  provided value(s) or does not consider the resource(s) acceptable, it
  should reject the request with an error response using the error code
  "invalid_target" as the value of the "error" parameter and can provide
  additional information regarding the reasons for the error using the
  "error_description"."

  Acceptable is one value, the identifier of a Resource Server the Client
  lists in the registry. One not registered, registered for other Clients
  only, malformed, or with a fragment is refused, as is more than one
  (REQ-RESOURCE-9).

- REQ-RESOURCE-5 (§2.1): "In the code flow (Section 4.1 of OAuth 2.0
  [RFC6749]) where an intermediate representation of the authorization
  grant (the authorization code) is returned from the authorization
  endpoint, the requested resource is applicable to the full authorization
  grant."

  The code records the Resource Server, and so does the Refresh Token
  Family it starts: each access token issued from the code, or by a
  refresh in the family, is for that Resource Server.

  Without `resource`, §2.1 lets the authorization server "process the
  request with no specific resource or by using a predefined default
  resource value". pulsar uses the default, its own issuer, for UserInfo
  (REQ-AT-5).

## The token request (§2.2)

- REQ-RESOURCE-6 (§2.2): "In the case of a "refresh_token" or
  "authorization_code" grant type request, such policy may limit the
  acceptable resources to those that were originally granted by the
  resource owner or a subset thereof."

  A token request may send the `resource` the code or Refresh Token Family
  was issued for, or none; any other, or one for a code issued without
  `resource`, gets `invalid_target`, and leaves the code or refresh token
  to be redeemed. So does a request for a code or family whose Resource
  Server the registry no longer lets its Client request, and a refresh
  for a scope that holds none of the Resource Server's scopes
  (REQ-RESOURCE-2).

- REQ-RESOURCE-7 (§2.2): "To the extent possible, when issuing access
  tokens, the authorization server should downscope the scope value
  associated with an access token to the value the respective resource is
  able to process and needs to know."

  An access token for a Resource Server holds, in `scope`, only the scopes
  granted that are that Resource Server's, and none of OpenID Connect's.
  The ID token is the same as without
  `resource`. UserInfo refuses this access token (REQ-AT-8), so a Client
  that wants the claims of `profile` or another OpenID Connect scope
  requests them in the ID token with the `claims` parameter, or in a
  request without `resource`. With `resource`, the `claims` parameter's
  `userinfo` member is ignored (REQ-CORE-45), and the End-User is not
  asked for the scopes of its claims.

- REQ-RESOURCE-8 (§2.2): "As specified in Section 5.1 of [RFC6749], the
  authorization server must indicate the access token's effective scope to
  the client in the "scope" response parameter value when it differs from
  the scope requested by the client."

  The token response's `scope` is always the access token's.

## Security considerations (§3)

- REQ-RESOURCE-9 (§3): "Although multiple occurrences of the "resource"
  parameter may be included in a token request, using only a single
  "resource" parameter is encouraged."

  Each access token pulsar issues names one Resource Server, or pulsar
  itself, in `aud`, so a request that sends `resource` more than once,
  even with one value twice, gets
  `invalid_target`, at either endpoint. Keycloak refuses it too, with
  `invalid_request`; §2 names `invalid_target` for a resource that is
  invalid. §3 allows the refusal: "an authorization server may be
  unwilling or unable to fulfill a token request with multiple
  resources."
