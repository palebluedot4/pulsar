# RFC 10017: OAuth 2.0 for Browser-Based Applications

Clauses of [RFC 10017](https://www.rfc-editor.org/rfc/rfc10017) that
pulsar, as the authorization server and UserInfo's resource server for a
browser-based OAuth client (§6.3), must or should meet. RFC 10017 puts the
backend-for-frontend architecture (§6.1) ahead of this one; pulsar
supports both, since a backend-for-frontend is a confidential Client and
needs nothing more of it.

- REQ-BROWSER-1 (§6.3.3.4): "The authorization server and the resource
  server MUST send necessary CORS headers (defined in [Fetch]) to enable
  the application to make the necessary cross-origin requests."

  The token endpoint, UserInfo and the JWK Set send them; discovery sends
  `Access-Control-Allow-Origin: *` already (REQ-DISC-14). The JWK Set,
  being public, sends `*` too. The token endpoint answers a request from
  the origin of one of the redirect URIs of a Client registered for
  `none`, and UserInfo one from the origin of a redirect URI of the Client
  the access token was issued to, whatever its method. §6.3.3.4 leaves the
  policy to the server, "a wildcard origin or a more restrictive
  configuration". The origins allowed are those node-oidc-provider allows
  by default, and need nothing registered beyond the redirect URIs
  ([research](../research/cors.md)).

  A preflight is approved for an origin some Client may send requests
  from, and the actual request is checked against its own Client, as
  §6.3.3.4 describes; node-oidc-provider and Keycloak approve a preflight
  from any origin. A public Client's token request is sent without a
  preflight, so one from an origin not allowed gets `invalid_request`
  before its code is redeemed or its refresh token rotated. Responses to an allowed origin,
  error responses included, carry `Access-Control-Allow-Origin`, and
  UserInfo's expose `WWW-Authenticate`. A request whose Client is not yet
  known, such as one without a `client_id` or with a token pulsar did not
  sign, gets no CORS headers.
