# RFC 7523: JWT Profile for OAuth 2.0 Client Authentication

Clauses of [RFC 7523](https://www.rfc-editor.org/rfc/rfc7523) that pulsar,
as an authorization server that authenticates Clients registered for
`private_key_jwt`, must or should meet. Its JWT authorization grant (§2.1)
is not offered, so only the clauses on client authentication are listed.

- REQ-JWTAUTH-1 (§2.2): "The value of the "client_assertion_type" is
  "urn:ietf:params:oauth:client-assertion-type:jwt-bearer". The value of
  the "client_assertion" parameter contains a single JWT. It MUST NOT
  contain more than one JWT."

  pulsar accepts the JWS Compact Serialization only, which holds exactly
  one signature.

- REQ-JWTAUTH-2 (§3): "The JWT MUST contain an "iss" (issuer) claim that
  contains a unique identifier for the entity that issued the JWT. [...]
  compliant applications MUST compare issuer values using the Simple
  String Comparison method [...]" and "For client authentication, the
  subject MUST be the "client_id" of the OAuth client."
- REQ-JWTAUTH-3 (§3): "The authorization server MUST reject any JWT that
  does not contain its own identity as the intended audience."

  pulsar's identity is either its token endpoint URL, which §3 names, or
  its issuer, compared as strings; `aud` may be a string or an array that
  holds one of them.

- REQ-JWTAUTH-4 (§3): "The authorization server MUST reject any JWT with an
  expiration time that has passed, subject to allowable clock skew between
  systems. Note that the authorization server may reject JWTs with an
  "exp" claim value that is unreasonably far in the future."

  pulsar allows no clock skew, so that a `jti` is kept exactly as long as
  its assertion could be accepted, and rejects an `exp` more than an hour
  away, which bounds how long a `jti` is kept.

- REQ-JWTAUTH-5 (§3): "The JWT MAY contain an "nbf" (not before) claim that
  identifies the time before which the token MUST NOT be accepted for
  processing."

  pulsar accepts an `nbf` up to a minute ahead of its own clock, for the
  clock skew between systems that REQ-JWTAUTH-4 allows; unlike skew on
  `exp`, this does not lengthen how long a `jti` is kept.

- REQ-JWTAUTH-6 (§3): "The authorization server MAY ensure that JWTs are
  not replayed by maintaining the set of used "jti" values for the length
  of time for which the JWT would be considered valid based on the
  applicable "exp" instant."

  pulsar does, in PostgreSQL, per Client, as OpenID Connect Core 1.0 §9
  requires (REQ-CORE-33).

- REQ-JWTAUTH-7 (§3): "The authorization server MUST reject JWTs with an
  invalid signature or MAC."
- REQ-JWTAUTH-8 (§3.2): "If the client JWT is not valid, the authorization
  server constructs an error response as defined in OAuth 2.0 [RFC6749].
  The value of the "error" parameter MUST be the "invalid_client" error
  code."
